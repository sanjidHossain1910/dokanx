# Future plans — recorded user preferences

## One-action offline shop to account transfer — 2026-10-23

The user authorizes moving an existing offline shop into a newly signed-in account without exporting/importing a backup file. Account Sync shows the offline shop photo, name, owner, address and record counts. An explicit transfer copies the entire validated BusinessData payload into the account workspace (including all supported current/future shop metadata), immediately publishes its first complete portable cloud snapshot with photos/QR, and enables the existing scheduled incremental sync only after publication and account activation succeed. This uses the existing backup/ownership APIs; subscription checkout and plan enforcement remain separate work.

The offline original is retained. Different occupied account-local data and an existing same-shop cloud head cannot be overwritten by first-transfer. A small account/shop-scoped recovery record preserves the restore generation and empty-head claim epoch, and the existing durable publisher preserves its request ID and pending archive. Connection loss, lost claim/upload replies or failed account activation can resume without creating duplicate shops/backups or reclaiming an already claimed epoch. Source/target edits and account/generation changes stop transfer. Device credentials and security remain outside BusinessData. Routine sync still excludes held carts and device-local drafts; the initial portable snapshot follows the existing manual-backup format.


## Incremental two-way cloud sync — 2026-10-21

The user clarified that the ten-minute interval should remain; they were reporting a failed scheduled upload, not requesting per-sale or five-second synchronization. The temporary immediate-sync changes were removed. An Android `ConnectException` is now classified as a connection failure. Legacy full-backup checkpoints also seed the first incremental comparison from the exact acknowledged archive's canonical record hashes, so a sale made before the first incremental check is treated as a change to its previous stock value rather than a conflicting new product. This does not replace phone business data or change the ten-minute scheduling policy.

The user now authorizes changed-record upload, server recovery snapshots and optional automatic download of remote changes. This supersedes the earlier no-merge/device-transfer deferral for nonconflicting records. Automatic checks use the existing ten-minute foreground interval; manual Sync always pulls, while automatic downloads are an explicit switch (off initially). Stable record IDs, canonical content hashes, a server generation/revision cursor, explicit deletion markers and atomic server validation replace record-count comparisons. Concurrent changes to the same record reject the entire transaction, including concurrent sales affecting the same product stock; no stock arithmetic or last-writer overwrite is inferred.

Record identities follow the business schema: due reminders use `invoiceId`, while the other synced collections use `id`. Reminders must round-trip without adding a synthetic ID. A capture failure on a valid shop containing a reminder was corrected in both the phone mapper and bundled server validator. Remote image copies are awaited before deleting their temporary source, matching the installed FileSystem API.

Photos use content hashes and upload once when missing. The first account download/bootstrap still needs the initial complete dataset. Routine sync sends only changed records/new images. PostgreSQL keeps current records, hashes and latest per-key changes/tombstones; the server builds complete `.dokanx` recovery snapshots, retaining the latest 30 automatic snapshots (older manually published backups are preserved). Existing development quotas still apply: 15 MB record payload, 60 MB archive, 3 MB per photo, 2,000 referenced photos, 60 MB per-shop asset table and 1 GB/100 total archive limits. Archives currently repeat photo bytes server-side; this change reduces network transfer, not all snapshot storage duplication.

Per-account/shop sync checkpoints and durable received changes live in a separate phone SQLite database, outside exported business data. Received changes are validated, photos localized, then committed through a workspace/restore-generation/local-payload guard; edits made during transfer are retained or produce a conflict. Device carts, notification read state, appearance preferences and credentials stay local. An explicit Account Sync adoption resets an obsolete checkpoint; file restore alone pauses uploads. Conflict resolution remains a deliberate review/download with an existing safety copy, rather than an automatic winner. Production hosting, subscriptions, AI and automatic reconciliation of simultaneous sales against the same stock remain deferred.

## Backend backup, restore and device transfer

The user wants to connect DokanX to a backend later so shop data can be backed up and restored on another device. Local file backup and restore were subsequently approved with the operations feature design. Backend authentication, cloud backup and remote synchronization are still deferred.

The future backup should include product details and IDs, photos, categories, units, quantities, thresholds, sales, purchases, expenses, customers, stock movement history and relevant shop settings. Restoring on another device must retain transaction relationships and product identities.

Preserve the offline-first repository boundary and stable IDs. Existing timestamps, deletion markers and repository revisions can support future synchronization, but a complete sync protocol and conflict policy have not been designed yet.

Product photos must be transferred as files or backend-managed assets. Current device-local photo URIs are not portable; a future restore must download/import photos into the destination device's app storage and rebuild the local references.

Future implementation should use versioned backup data and migrations, validate restores before replacing local data, avoid duplicate records on retry and preserve history. Backend provider, account/shop ownership, backup scheduling, encryption and conflict handling remain decisions for that future task.

Current status: native local persistence with manual, versioned `.dokanx` file backup/restore. Backups include photos and wallet QR files, drafts, history, business settings and language/appearance preferences. Restore validates references and asset hashes, stages new assets under a unique document folder, then atomically replaces the shop payload. A safety backup is created first and stale reviews cannot overwrite newer changes. No cloud backup or remote synchronization is enabled. Bluetooth printer addresses are device-specific and deliberately cleared on restore.

The app now targets Android phones and iPhone only. Native SQLite/document storage remains the persistence boundary; browser-only storage and UI adapters are no longer maintained. Preserve the native database and document-file migration requirements above when adding future backups.

Profile settings add `businessSettings` (invoice prefix/message, default sale discount, new-product low-stock limit and date/time display preferences), wallet `isDefault` flags and an optional invoice `receiptFooter` snapshot. Future backup/restore must preserve these along with existing identity and payment data. Appearance and language continue to use their existing local preference keys.

Printed receipts now follow the user's smaller fixed format: shop name, Transaction ID, original sale/purchase date/time, products with quantities and prices, total, then `Thank you`. Old footer snapshots remain in historical data but are not printed. Payment, customer, contact, tax and discount sections are omitted from printed receipts.

Operations data adds immutable `customerCollections`, `supplierPayments`, `saleReturns`, `cashDays` and remaining `productBatches`, with optional invoice batch allocations and purchase batch metadata. Keep stable IDs and allocation links intact in future cloud migrations. Returns leave original invoice/sale snapshots unchanged; reports net out returns on the return date. Expired lots are excluded from sales by default; batch assignment labels existing stock, while received purchases add stock and lots together.

Product metadata now includes optional `wholesalePrice` (positive BDT minor units; absent means wholesale is disabled) and `isFavorite`. Cart/invoice lines may contain `priceType`, with absent values interpreted as legacy retail. Completed invoices keep their unit-price snapshots even if wholesale is later disabled. `heldSales` contains saved cart IDs, product/photo snapshots, customer IDs, discount/tax settings, labels and hold timestamps. Hold/resume never writes stock or financial records. Resume reviews current stock and prices; unavailable wholesale falls back to retail with a visible review notice. Backups must preserve held carts and their retained photos as well as these product/line fields. Keep held, active cart and completed invoice IDs disjoint.

Offline shop registration now stores `shopId`, `shopActive`, owner name, contact number, address, shop photo URI and registration timestamp. Future backups must preserve that identity and registration state, transfer the shop's `SHOP-` photo file from `product-photos/`, and rebuild its URI. Login/signup are currently replaced by this local setup flow; it does not create a backend account. Wallet account names are now optional saved metadata, and an enabled wallet requires a valid phone number while QR images are optional.

Payment setup now also contains enabled bKash/Nagad methods, account numbers and QR images. Future backup/restore must include these settings and transfer QR files from `payment-qr/`, rebuilding local URIs on the destination device. The reusable payment setup currently lives in Profile; connect it to account onboarding when that flow is implemented. Card support is deferred.

Purchasing now also stores suppliers with outstanding balances, a purchase draft, immutable supplier/product invoice snapshots, payment details, receipt status and stock movement links. Future backup/restore must retain supplier and purchase invoice IDs and these relationships. Purchase draft/receipt photos reuse retained product photo files. Pending invoices must remain pending after restore and must not receive stock twice.

Stock counts now add optional immutable stockCounts records (stable IDs, SC numbers, timestamps, notes and per-product original name/photo/unit/before/counted/reason snapshots). Changed items link to stockMovements through movementId and stockCountId. Preserve both sides of these links and snapshot photos during backup/restore and future synchronization. Counts change inventory and batch quantities atomically without creating sales, payments or expenses. Unchanged items are recorded without stock movements; retries must not apply a saved count again. Unsaved counting inputs remain local to the open form and are not backed up.

Security is device-local and separate from BusinessData and .dokanx backups. Optional App Lock uses system authentication; Sales & Profit can be off, use system authentication, or use a separate six-digit PIN. SecureStore contains one versioned atomic record, including a random-salted PBKDF2-SHA256 verifier and persisted retry cooldowns. No entered PIN, phone credential, unlocked session flag, or temporary recovery authorization is exported. Restoring shop data retains the receiving phone's security configuration; a new installation configures its own security. OS verification is required for changes or recovery, and a one-use expiring proof authorizes setting a new report PIN. These are UI access controls, not encryption of the business SQLite database or exported backups. Future sync must never upload device-local security secrets or unlock grants.

PIN performance update: new verifiers use scrypt (N=32768, r=8, p=3; 32 MiB work memory) with a random salt, progress, cancellation and a 90-second hashing deadline. Existing PBKDF2-SHA256 verifiers remain readable and are never silently reset. The verifier algorithm and cost parameters stay in the device-local security record; business backup exclusion is unchanged.

PIN UX update: newly created report PINs have exactly four digits (digits: 4 in the verifier). The fourth keypad digit immediately advances setup, confirms/saves, or attempts unlock; no submit button is required. Legacy six-digit verifiers without the digits field remain protected and readable. The UI requests OS-verified replacement with a new four-digit PIN, rather than truncating, discarding or silently unlocking a legacy PIN.

Current PIN verification supersedes the slow-KDF updates above: new four-digit records use device-hmac-sha256, with a random salt and a separate random 256-bit device key stored only in SecureStore (dokanx.security.pin-key.v1). The business payload, backups and PIN verifier never contain this key. Verification performs one HMAC rather than a JS password-stretching loop. This intentionally relies on OS-keystore protection, device-local UI access controls and persisted attempt limits; it is not a portable password verifier or protection against a compromised/rooted device. Older scrypt/PBKDF2 records remain locked and request OS-authenticated PIN replacement before the new fast path is used. Do not truncate PINs, silently reset protection, export the key, or recreate a missing key during verification. Failed setup leaves the old security record intact. Setting a new PIN also rechecks its one-use OS authorization immediately before saving.

Product transparency fix: newly cropped product/shop photos are lossless PNG with alpha preserved. PNG output is downscaled from the original square crop until within 1,000,000 bytes; preview and stored file are identical. New prepared photos carry format=png and save under product-photos/*.png; legacy JPEG files/URIs remain supported and are not rewritten. Backups and future migrations must transfer both formats, preserving original bytes and rebuilding URIs. Already flattened JPEG backgrounds cannot be recovered without reselecting the original transparent photo.

Smart restock now persists optional restock v1 in BusinessData: planning settings (history window, target/lead/safety days, optional budget), product rules (canonical unit, pack size, optional delivery/shelf-life/max-order/preferred supplier) and a manual buy list (product ID, unit, quantity). Keep these in local backup and future device transfers; stale unit entries remain readable and require review instead of breaking old data. New estimates never overwrite manual quantities. An explicit hand-off atomically creates a purchase draft for selected list items and removes only those items; it never receives stock, pays a supplier or overwrites another draft. Offline estimates use complete local days, unit-matched net sales, stock availability reconstructed from movement/legacy records, pending orders and expiry/pack/budget guards. Limited evidence stays manual.
Online AI remains deferred. src/restock/prediction.ts defines a versioned aggregate snapshot, input fingerprint (including private cost-change guards), provider adapter, bounded/cancellable request and validated source-tagged result. No backend, provider key, network request, remote result or data sharing is configured in the current UI. A future opt-in backend must keep credentials server-side, exclude identity/payment/PIN/photo data, reject outdated revisions/units/unsafe quantities and keep a fresh local estimate available on error or no connection. Remote results never edit the buy list without explicit review. Compare prediction quality with realised demand before promising improvement.

Optional payment follow-ups now store dueReminders alongside business data: invoiceId, local calendar dueDate, remind flag and optional authored notifyAt instant. They reference originally due customer invoices and never rewrite financial snapshots. Backups transfer these plans; current remaining amounts are derived from collections/returns. Phone permission, notification queue IDs and delivery receipts are device-local and excluded from backups. Restoring another shop payload reconciles/removes old phone requests and schedules only future unpaid plans after permission is available. No cloud service, customer messaging or automatic collection is enabled.

## Cloud subscription and backup interval — confirmed 2026-10-21

Subscription is cloud-only; offline product count remains unlimited. Cloud tiers are based on product count (examples: 100, 500, 1,000), with pricing/count semantics/storage/retention/AI allowances to be decided. Never block local sales or product creation because of a cloud limit or expiry. Do not mark a partial over-limit archive as a complete recovery backup.

Do not back up after every sale. Default proposed user-selected interval is 10 minutes: while active, check for backup-relevant changes since the last successful snapshot; upload one consolidated backup only if changed. Keep immediate local saves. No-change intervals create no uploads/versions. Offline/missed intervals are coalesced into one overdue check on reconnect/foreground. One backup at a time, bounded retry/backoff, and checkpoints advance only after server validation; changes made during upload remain pending. Manual Backup Now remains available. Exact 10-minute execution while backgrounded/terminated is not guaranteed by phone OS scheduling. This records design decisions only; cloud implementation remains deferred.

## Explicit conflict decisions — 2026-10-23

User-authorized sync review now stores before-values in the local outbox, an audit of retired operations and the user's whole-group choice in SQLite, plus server before/after history with editor device metadata. These are sync infrastructure and stay outside BusinessData/portable exports. The mandatory safety archive uses the existing complete backup format, preserving photo bytes and shop metadata. Decisions never export device security. Original values for pre-migration records may be unavailable; label this honestly rather than guessing from timestamps. Server record hashes and generation fences remain authoritative.

Payment conflict update: explicitly merging separate customer/supplier settlements is now authorized. Keep stable payment IDs and original invoice allocations intact in future exports/migrations. Recompute the cached party balance from the reviewed cloud balance and new local settlement events; never sum cached balance snapshots. Exact duplicate IDs count once. Overpayments, edited/deleted payments, unknown baselines, mixed operation groups and invalid invoice/cash allocations remain manual review, not automatic merging. No new BusinessData fields, archive format or server schema are introduced by this update. The local conflict audit now also accepts choice=merge.

Independent-sync update: conflicts now pause only their connected operation groups. Other uploads and downloads continue on the configured foreground schedule. Account-scoped incremental SQLite checkpoints retain deferred remote deltas until linked local changes are resolved, so an advanced server cursor cannot forget held data. This metadata is device-local sync infrastructure, not part of BusinessData, portable backups, PIN data or cross-account restores. No new backend schema is required.

Allocation conflict correction: explicit Keep both payments may now reassign only the new, still-local settlements to the latest unpaid bills via the existing oldest-bill-first allocator. Preserve their payment identity, total, method, reference and timestamp, accepted cloud settlements, and original invoice snapshots. Previous local allocations remain recoverable through the safety archive and conflict audit. Closed cash-day totals must never be silently recalculated/reopened. Portable backups carry the chosen settled allocations normally; this introduces no new BusinessData field or archive version.
